# «Компас» — локальный макет сервиса формирования ИПР

Макет воспроизводит сквозной сценарий: форма **«ПЛАН РАЗВИТИЯ»** (наша заглушка) →
кнопка **«Сформировать с помощью Компаса»** → диалоговое формирование индивидуального
плана развития с заземлением на справочники (RAG) → экспорт (DOCX/JSON) →
отправка руководителю на согласование.

Всё поднимается одной командой на одной машине, без внутреннего контура компании.

> **Данные в макете синтетические.** Роли, компетенции, активности и сотрудники
> вымышлены. Реальные ИПР и результаты оценки во внешнюю LLM не отправляются.

## Быстрый старт

```bash
cp .env.example .env
# впишите LLM_API_KEY и свой JWT_SECRET (минимум 32 символа)
docker compose up --build
```

| Сервис | Адрес | Назначение |
|---|---|---|
| Заглушка «ПЛАН РАЗВИТИЯ» | http://localhost:8081 | Форма и точка входа |
| «Компас» (SPA) | http://localhost:4200 | Чат и панель ИПР |
| «Компас» (API) | http://localhost:8090/api | REST |
| PostgreSQL | localhost:5433 | `kompas` / `kompas` / `kompas` |

Сценарий: открыть http://localhost:8081, выбрать демо-сотрудника в белом поле шапки,
нажать **«Сформировать с помощью Компаса»**.

> Хостовые порты 8090 и 5433 выбраны, чтобы не конфликтовать с другими сервисами
> на машине (8080 и 5432 часто заняты). Внутри сети compose бэкенд слушает 8080.

## Офлайн-режим (без ключа и без сети)

```bash
SPRING_PROFILES_ACTIVE=local docker compose up --build
```

Профиль `local` принудительно включает `MockLlmClient` и локальные эмбеддинги —
даже если `LLM_PROVIDER` задан в `.env`. Весь сценарий проходится целиком.

## Конфигурация (`.env`)

| Переменная | Назначение |
|---|---|
| `LLM_PROVIDER` | `openrouter` или `mock` |
| `LLM_BASE_URL` | Базовый URL OpenAI-совместимого API |
| `LLM_API_KEY` | Ключ провайдера |
| `LLM_MODEL` | Модель, по умолчанию `openai/gpt-4o-mini` |
| `LLM_FALLBACK_MODEL` | Запасная модель при лимите провайдера основной (пусто — без запасной) |
| `JWT_SECRET` | Общий HMAC-секрет заглушки и «Компаса», ≥ 32 символов |
| `KOMPAS_FRONTEND_URL` | Куда заглушка редиректит с токеном |
| `LEGACY_IMPORT_URL` | Куда «Компас» возвращает готовый план |
| `SPRING_PROFILES_ACTIVE` | `local` — офлайн, `prod` — внешний LLM |

Секреты живут только в `.env`, он в `.gitignore`.

## Как устроен диалог

Шесть стадий: `CONTEXT` → `GAP_ANALYSIS` → `INTERESTS` → `DRAFT` → `REFINE` → `FINALIZE`.

На каждом ходу оркестратор собирает промпт из шаблона стадии, состояния сессии,
RAG-контекста и истории, вызывает LLM и разбирает ответ. Модель отвечает одним
JSON-объектом с текстом для чата и (при изменении) полным черновиком ИПР.
Если формат нарушен — один корректирующий повтор, затем текст показывается как есть,
а стадия не двигается.

**Заземление проверяется дважды:** системный промпт запрещает коды вне контекста,
а `DraftParser.sanitize()` вырезает из черновика всё, чего не было в справочниках,
с предупреждением в лог.

**Целевую роль можно сменить прямо в диалоге.** Если сотрудник не согласен с ролью
из токена входа, ассистент не считает это подтверждением, а предлагает роли его трека
из справочника. Названная роль приезжает в поле `targetRole` ответа, оркестратор
сверяет её со справочником и переключает сессию — дальше RAG отдаёт компетенции
уже новой роли. Черновик, собранный до переключения, в этот ход не применяется:
он был заземлён на прежнюю роль.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/sessions` | Создать сессию по токену входа, вернуть `accessToken` |
| `GET` | `/api/sessions/{id}` | Стадия, история сообщений, текущий черновик |
| `POST` | `/api/sessions/{id}/messages` | Ход диалога |
| `GET` | `/api/idp/{id}` | Получить ИПР |
| `PUT` | `/api/idp/{id}` | Ручная правка черновика |
| `POST` | `/api/idp/{id}/export?format=docx\|json` | Экспорт |
| `POST` | `/api/idp/{id}/handover` | Ссылка на форму «ПЛАН РАЗВИТИЯ» с перенесённым планом |
| `POST` | `/api/idp/{id}/submit` | Отправить на согласование |
| `GET` | `/api/reference/roles/{id}/competencies` | Компетенции роли |
| `GET` | `/api/reference/activities` | Каталог активностей |
| `GET` | `/api/health` | Провайдеры и размер RAG-индекса |

Все вызовы, кроме `POST /api/sessions` и `/api/health`, требуют заголовок
`Authorization: Bearer <accessToken>`.

## Что не входит в макет — [POST-MVP]

Клиент `ai.redelephant` и внутренний контур; автоматический трекинг сроков
и напоминания; загрузка готового ИПР; мониторинг портала Locus; кабинет руководителя.

Возврат приоритетов в форму старого сервиса ТЗ относило к `[POST-MVP]`, но он
сделан: кнопка **«Перенести в ПЛАН РАЗВИТИЯ»** отдаёт подписанную ссылку, по которой
форма открывается с уже разложенными по её колонкам приоритетами.

Форма устроена так: колонка «Цели по развитию» — выпадающий список с фиксированным
справочником рубрик, а под каждой целью разворачивается своя таблица развивающих
действий (инструмент 70-20-10, конкретное действие, срок, статус). «Компас» заполняет
и то и другое: относит приоритет к рубрике и собирает под ним действия, сверяя
инструменты и коды активностей со справочниками. Контракт —
в [`docs/integration.md`](docs/integration.md).

В макете план переносится в отображение формы: своего хранилища у заглушки нет.

Модель данных развивающих действий (срок и статус выполнения у каждого) и статусов
согласования, а также интерфейсы
`LlmClient`, `EmbeddingClient`, `VectorStore`, `EntryTokenVerifier`, `ApprovalNotifier`
заложены сразу — POST-MVP добавляется без ломающих миграций.
