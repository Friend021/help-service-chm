# Компас — полный процесс работы (детальная спецификация)

Документ отражает **фактически реализованный** сквозной процесс «Компаса»: от перехода из
системы «План развития» (devplan) до возврата готового ИПР на согласование. Включает актёров,
эндпоинты, данные, развилки, кэш и **точные промты LLM из кода**. В конце — сверка со схемой
`Схема работы_1.drawio` и открытые вопросы для боевой интеграции.

---

## 0. Компоненты и порты (dev)

| Компонент | Что это | Порт | Технологии |
|---|---|---|---|
| **«План развития» (devplan)** | Внешняя система-источник (`legacy-stub`) | `:8081` | Spring Boot, Thymeleaf, Spring Security (OIDC-клиент) |
| **Keycloak** | Единый вход (SSO). Dev — `auth-mock` | `:3000` | Node/Fastify (мок OIDC: discovery, JWKS, auth-code+PKCE, password, SSO-cookie) |
| **Компас — фронт** | SPA мастера ИПР (`frontend-v2`) | `:4200` | Angular 22, keycloak-js, SSE через fetch |
| **Компас — бэк** | API `/api/v1` + живой LLM (`backend`) | `:8090` | Spring Boot 3.3, пакет `ru.cft.kompas.v1.*` |
| **Postgres** | БД (роли, компетенции, сессии, ИПР, RAG) | `:5433` | Postgres 16, Flyway |
| **LLM** | Генерация опросника/плана/правок | — | OpenRouter, модель `openai/gpt-4.1` (fallback `gpt-4o`) |

**Авторизация:** все `/api/v1/**` защищены **Keycloak RS256** (валидация по JWKS). Контекст сотрудника
приходит отдельным **entry-токеном HS256** из devplan (общий секрет). Легаси-контракт `/api/*`
(вход по собственному токену) не тронут.

**Стадии мастера** (бэк `DialogStage` → фронт `WorkflowStage`, всего 5 шагов):
`CONTEXT`→STAGE_1_CONTEXT · (не подтверждён)→STAGE_1_2_ONBOARDING · `GAP_ANALYSIS/INTERESTS`→STAGE_2_QUESTIONNAIRE ·
`DRAFT`→STAGE_3_DRAFT_GEN · `REFINE`→STAGE_4_REFINEMENT · `FINALIZE`→STAGE_5_COMPLETED.

## 1. Сквозной процесс (шаг за шагом)

Легенда актёров: **[Ч]** человек · **[DP]** «План развития» · **[KC]** Keycloak · **[Ф]** фронт Компаса ·
**[Б]** бэк Компаса · **[LLM]** модель.

### Шаг 1. Вход в «План развития» (SSO)
- **[Ч]** открывает `http://localhost:8081`.
- **[DP]** (Spring Security `oauth2Login`) — любая страница требует входа → редирект на **[KC]**.
- **[KC]** показывает форму «Единый вход» → `demo/demo` → ставит **SSO-cookie `KC_SESSION`** (HttpOnly,
  SameSite=Lax, 8ч) и возвращает код; devplan обменивает код (PKCE) → пользователь авторизован.
- Итог: в браузере есть сессия Keycloak — дальше вход в Компас будет **автоматическим**.

### Шаг 2. Старт сессии «через Компас»
- **[Ч]** на странице «Создать ИПР» выбирает сотрудника и жмёт **«Создать через Компас»**.
- **[DP]** `GET /kompas?employee=<extId>` → подписывает **entry-токен (HS256)** с claims:
  `employeeExternalId, fullName, currentPosition, targetRole, careerTrack, managerFullName,
  managerExternalId, iss=legacy-plan-razvitiya` (TTL 10 мин) → `302` на
  `http://localhost:4200/entry?token=<JWT>`.

### Шаг 3. `/entry` и автоматическая авторизация в Компасе
- **[Ф]** маршрут `/entry` (`EntryComponent`): сохраняет `token` в `sessionStorage`.
- Если не авторизован → `keycloak.login('/entry')` → редирект на **[KC]** `/auth`. Там **уже есть
  `KC_SESSION`** → Keycloak **сразу отдаёт код без формы** (тихий вход) → назад на `/entry?code=…`.
- keycloak-js (режим `responseMode:'query'`, без iframe-проб) обменивает код → получает токены.
- **[Ф]** → `POST /api/v1/session/entry` с `Authorization: Bearer <KC access>` и телом `{token}`.

### Шаг 4. Бэк принимает контекст
- **[Б]** `V1SessionController.entry`: валидирует entry-токен (`JwtEntryTokenVerifier`) → `EntryContext`.
- `V1SessionService.applyEntry(principal, ctx)`: заводит/находит сотрудника по **Keycloak sub**,
  проставляет ФИО/руководителя/должности из токена, резолвит текущую и целевую `JobPosition`,
  открывает/обновляет активную `DialogSession`, стадия `GAP_ANALYSIS`, `contextConfirmed=false`.
- Ответ — тот же, что `GET /session/context`: `{context{employeeId,fullName,managerFullName,
  currentPosition,targetPosition,returnUrl,isNewEmployee,...}, scenario, stage, returnUrl}`.
- ⚠️ **Расхождение со схемой:** в схеме контекст берётся из Orgstructure `VW_COMPASS_EMPLOYEES`;
  у нас — из entry-токена devplan. Для боя — решить источник.

### Шаг 5. Подтверждение должностей (онбординг, всегда)
- **[Ф]** `IdpEntryComponent`: пока `contextConfirmed=false` бэк отдаёт `STAGE_1_2_ONBOARDING` →
  ведёт на `/idp/onboarding`.
- **[Ч]** на экране «Подтверждение должностей»: **текущая** — read-only из контекста; **целевая** —
  `mat-select` из `dictionaries.targetRoles` (все роли профилей, отсортированы по семейству+грейду),
  по умолчанию — из контекста. Подтверждает → `POST /api/v1/session/context/manual
  {currentPosition,targetPosition}` → бэк ставит `contextConfirmed=true`, стадия `GAP_ANALYSIS` →
  фронт идёт на опросник. (Смена целевой роли сбрасывает кэш навыков на фронте.)

### Шаг 6. Справочники
- **[Ф]** шелл при загрузке зовёт `GET /api/v1/idp/dictionaries` →
  `{directions[11], priorities[Высокий/Средний/Низкий], developmentTools[3], stages[6], targetRoles[16]}`.
  `targetRoles` фильтр — `type∈{TARGET,BOTH}`, порядок — по `careerTrack` + `id` (семейство+грейд).

### Шаг 7. Опросник — генерация из профиля (ключевой механизм)
- **[Ф]** `POST /api/v1/chat/init-assessment` (**SSE**).
- **[Б]** `V1QuestionnaireService.forTargetRole(session)`:
  1. Если у целевой роли **уже есть компетенции** (`CompetencyRepository.findByRoleIdOrderByCodeAsc`)
     → отдаёт их (кэш-хит, без LLM).
  2. Иначе — **[LLM]** генерит компетенции из профиля роли (`jobDescriptionRef`) и **кэширует** их как
     строки `Competency` (`code = AUTO-<roleId>-NN`, `targetLevel` = грейд). Дальше — всегда кэш.
- SSE: `STAGE_UPDATE(STAGE_2_QUESTIONNAIRE)` → `MESSAGE_DELTA`(приветствие) → `QUESTIONNAIRE_READY{skills}` → `DONE`.
  `skills[]` = `{skillId=code, skillName=name, description, rating:null}`.
- ⚠️ Это **ровно шаг 8 схемы** («промт: на основе ПД составь вопросы»), но у нас — **в рантайме и с кэшем**,
  поэтому каждый грейд даёт свой опросник (грейды различаются сами собой).

### Шаг 8. Самооценка
- **[Ч]** на `/idp/assessment` оценивает каждую компетенцию 1–5 (звёзды). Описание показывается целиком.
- Оценки хранятся на фронте (`ratings: Map<skillId,1..5>`), отправятся на генерацию черновика.
- ⚠️ Переспроса при «невалидном ответе» (ромб из схемы) нет — просто требуется оценить все.

### Шаг 9. Генерация черновика ИПР (живой LLM)
- **[Ф]** `POST /api/v1/chat/generate-draft {ratings:[{skillId,rating}]}` (**SSE**).
- **[Б]** `V1DialogService.generateDraft` (не-mock путь `generateDraftViaLlm`): собирает промт из
  профиля роли + самооценки (слабые компетенции) + категорий + инструментов + сегодняшней даты →
  **[LLM]** → JSON-план → нормализация (rank 0..2; инструмент из справочника; **snap категории**
  к справочнику; **прошедшие сроки → +3 мес**) → сохранение в ИПР (`IdpService.applyDraft`),
  стадия `REFINE`.
- SSE: `STAGE_UPDATE(3)` → `MESSAGE_DELTA`(ассистент) → `PLAN_DRAFT_UPDATE{plan}` → `STAGE_UPDATE(4)` → `DONE`.
- mock-провайдер → старый оркестратор (фолбэк).
- Соответствует шагам **11 (приоритеты)** и **12 (сборка ИПР JSON)** схемы. ⚠️ «Заземление: только из
  справочников» — **ослаблено**: категории и инструменты строго из справочников, цели/действия AI
  пишет свободно (каталога активностей нет).

### Шаг 10. Черновик: просмотр и ручное редактирование
- **[Ф]** `/idp/draft` (`DraftComponent`): главная цель, направления (категория, приоритет, описание),
  действия (инструмент, срок, описание, комментарий). Можно: менять поля, добавлять/удалять
  направления и действия, **переупорядочивать (drag-and-drop)**, сохранять (`PUT /api/v1/idp/draft`).

### Шаг 11. Диалог-корректировка с AI (применяет правки)
- **[Ч]** пишет правку в чат: «добавь направление по X», «сдвинь сроки», «повысь приоритет 1-го».
- **[Ф]** `POST /api/v1/chat/refine-draft {message}` (**SSE**).
- **[Б]** `V1DialogService.refine` (`refineViaLlm`): даёт **[LLM]** текущий план (JSON) + запрос +
  справочники + дату, просит **ПРИМЕНИТЬ** правку и вернуть `{reply, plan}`; план нормализуется и
  сохраняется, `reply` идёт в чат. Без отговорок.
- SSE: `STAGE_UPDATE(4)` → `PLAN_DRAFT_UPDATE{plan}` → `MESSAGE_DELTA`(reply) → `DONE`.

### Шаг 12. Подтверждение
- **[Ч]** «Готово, перейти к подтверждению» → `/idp/completion` (`STAGE_5_COMPLETED`): read-only обзор
  плана (карточки без drag), валидность (`isValid`). Опционально `POST /api/v1/chat/confirm`.

### Шаг 13. Экспорт обратно в «План развития»
- **[Ф]** `POST /api/v1/idp/export {plan}`. **[Б]** валидирует «полноту» (непустые mainGoal/направления/
  действия/сроки; иначе `422`), сохраняет, стадия `FINALIZE`, и строит **handover-токен (HS256)**
  (`HandoverTokenIssuer`) с приоритетами (метка **Высокий/Средний/Низкий** по порядку) → `{success,returnUrl}`.
- **[Ф]** `window.location.href = returnUrl` → переход на **[DP]** `/import?token=…`.

### Шаг 14. Приём плана в devplan и согласование
- **[DP]** `/import`: проверяет handover-токен (`HandoverTokenVerifier`), раскладывает план в форму
  «Плана развития» — направления, **категории**, **приоритеты** (дропдаун заполняется), действия
  (инструмент, срок). Правая панель-дерево отражает направления и действия со статусом.
- **[Ч]** «Отправить на согласование» → жизненный цикл devplan: Создание → Согласование →
  Согласован, не начат → В процессе → Выполнен.

## 2. Точные промты LLM (из кода, дословно)

Общие параметры: модель из `kompas.llm.*` (сейчас `openai/gpt-4.1`), `temperature` из конфига
(0.3), `response_format=json_object` (включается `OpenRouterClient` при `json-mode=true`).
Парсинг JSON: снять ```-ограждения, взять объект от первого `{` до последнего `}`.

### 2.1. Опросник — `V1QuestionnaireService`
**SYSTEM:**
```
Ты — методолог по управлению персоналом. По профилю должности формируешь компактный список
ОЦЕНИВАЕМЫХ компетенций для самооценки сотрудника.
```
**USER:**
```
Целевая роль: {title}

Профиль должности:
{jobDescriptionRef}

Сформируй 6–8 ключевых компетенций (умение/способность, не факт-знание) именно для этой роли и её
грейда. Для каждой: 'name' (2–6 слов, без слова «Знание…») и 'description' (1 предложение — что
значит владеть на уровне этой роли). Компетенции должны отражать масштаб и самостоятельность именно
этого грейда. Верни строго JSON: {"competencies":[{"name":"...","description":"..."}]}
```

### 2.2. Черновик ИПР — `V1DialogService.generateDraft`
**SYSTEM (`DRAFT_SYSTEM_PROMPT`):**
```
Ты — опытный наставник по развитию сотрудников. Ты составляешь индивидуальный план развития (ИПР),
которым человек реально будет пользоваться: конкретные направления по реальным пробелам, измеримые
цели и практические шаги. Пиши по-деловому и конкретно, без шаблонных формулировок.
```
**USER (`buildDraftUserPrompt`):**
```
Сегодняшняя дата: {today}. Все сроки должны быть ПОЗЖЕ этой даты и не дальше {today+6мес} (в пределах 6 месяцев).

Сотрудник развивается в сторону роли «{targetRole}».

Профиль роли:
{jobDescriptionRef}

Самооценка сотрудника по компетенциям (1–5, чем ниже — тем слабее владение):
- {competencyName}: самооценка {rating}/5
... (по каждой компетенции)

Доступные КАТЕГОРИИ направления развития (поле "goal" — выбери для каждого направления ОДНУ,
наиболее подходящую ПО СМЫСЛУ строго из этого списка; не ставь везде одну и ту же):
- {11 категорий}

Доступные ИНСТРУМЕНТЫ развития (поле "developmentTool" — выбери строго из этого списка):
- Развитие на рабочем месте
- Развитие через других
- Развитие через учебные программы

Составь индивидуальный план развития на 3–6 месяцев. Требования:
- Возьми 2–3 САМЫЕ СЛАБЫЕ компетенции (низкая самооценка) — по одному направлению на каждую.
- "rank": приоритет направления — 0 (высокий), 1 (средний), 2 (низкий); выше приоритет у более слабых компетенций.
- "goal": категория направления строго из списка категорий, подходящая по смыслу именно к этой компетенции (НЕ ставь везде «Развитие личностных компетенций»).
- "description": конкретная цель развития — что сотрудник НАУЧИТСЯ ДЕЛАТЬ и какой наблюдаемый результат получит на рабочих задачах. НЕ пиши «увеличить уровень компетенции X до N/5».
- "tasks": 2–3 конкретных развивающих действия. Для каждого: "developmentTool" строго из списка инструментов; "description" — предметное действие (что именно сделать на практике, с привязкой к рабочим задачам); "deadLine" — реалистичный БУДУЩИЙ срок (после {today}, до {today+6мес}) в формате ISO-8601 UTC, например "{today+6мес}T12:00:00Z"; "comment": "".
- "mainGoal": одна фраза — общая цель плана (переход на роль «{targetRole}»).

Верни СТРОГО JSON:
{"mainGoal":"...","directions":[{"rank":0,"goal":"...","description":"...","tasks":[{"developmentTool":"...","description":"...","deadLine":"2026-...Z","comment":""}]}]}
```

### 2.3. Правка плана — `V1DialogService.refine`
**SYSTEM (`REFINE_SYSTEM`):**

Ты — помощник по редактированию индивидуального плана развития (ИПР). Пользователь просит внести
правку — ты ВЫПОЛНЯЕШЬ её, меняя план, а не отказываешься и не переспрашиваешь, если запрос понятен.
Возвращаешь ВЕСЬ обновлённый план и короткое подтверждение.
```
**USER (`buildRefineUserPrompt`):**
```
Текущий черновик ИПР (JSON):
{currentPlanJson}

Доступные КАТЕГОРИИ направления (поле "goal" — выбирай подходящую по смыслу из списка):
- {11 категорий}
Доступные ИНСТРУМЕНТЫ развития (поле "developmentTool" — строго из списка):
- {3 инструмента}
Сегодняшняя дата: {today}. Любые новые/изменённые сроки — будущие (после сегодня), в пределах 12 месяцев, в формате ISO-8601 UTC (например "{today+3мес}T12:00:00Z").

Запрос пользователя:
"{message}"

Примени этот запрос к плану: добавь, измени или удали направления и действия так, как просит
пользователь. Если тема запроса отсутствует в справочниках — всё равно добавь соответствующее
направление/действие, подобрав ближайшую по смыслу категорию из списка и инструмент из списка.
Не отказывайся и не задавай уточняющих вопросов, если запрос понятен. Остальные части плана
сохрани без изменений.

Верни СТРОГО JSON:
{"reply":"<одно короткое предложение: что именно изменил>","plan":{"mainGoal":"...","directions":[{"rank":0,"goal":"...","description":"...","tasks":[{"developmentTool":"...","description":"...","deadLine":"...Z","comment":""}]}]}}
```

## 3. Данные и справочники

- **Роль (`JobPosition`)**: `title, type(CURRENT/TARGET/BOTH), careerTrack, jobDescriptionRef` —
  последнее хранит **полный текст профиля должности** (опыт + функции + знания + навыки грейда),
  он же вход для генерации опросника и grounding. Загружено **16 ролей** (4 профиля × 4 грейда) из
  `Профили должности/*.xlsx` (парсер — Node+SheetJS; сид `reference-data.yml`).
- **Компетенция (`Competency`)**: `code(unique), name, description, role_id, targetLevel`. Генерятся
  лениво из профиля роли при первом опроснике, кэшируются (`AUTO-<roleId>-NN`). Их же дословно видит
  LLM при генерации плана.
- **Модель плана фронта**: `{mainGoal, directions:[{rank 0..2, goal(категория), description,
  tasks:[{developmentTool, comment, deadLine(ISO UTC), description}]}]}`.
- **Справочники**: 11 категорий целей (`GoalCategoryCatalog`), 3 инструмента (`DevelopmentInstrument`),
  приоритеты Высокий/Средний/Низкий. `GoalCategoryCatalog.snap` «примагничивает» перефразированную
  моделью категорию к ближайшей из справочника (иначе дропдаун пустой).
- **RAG**: `reference_chunk` строится из `jobDescriptionRef` и описаний компетенций (вектор —
  локальные эмбеддинги). На генерацию плана компетенции идут **дословно** (не через вектор).

## 4. Сверка со схемой `Схема работы_1.drawio`

| Шаг схемы | Статус | Комментарий |
|---|---|---|
| 1 вход из devplan → старт | ✅ | «Создать через Компас» |
| 2 авто-авторизация (Keycloak?) | ✅ | Keycloak + SSO (один вход в devplan → авто в Компас) |
| 3 контекст (Orgstructure `VW_COMPASS_EMPLOYEES`) | ⚠️ | У нас — из entry-токена devplan. Решить источник для боя |
| 4 окно подтверждения должностей | ✅ | Текущая авто/read-only, целевая из списка |
| 5 целевая из списка (profiletree) | ✅ | Дропдаун ролей из профилей |
| 6 фиксация ключевой цели | ⚠️ | У нас mainGoal авто-генерится и редактируется; отдельного шага нет |
| 7 поиск профиля + «найден?» / Fallback | ⚠️ | Профиль всегда есть у засеянной роли; **fallback/ручной ввод роли не делали** |
| 8 промт: вопросы из ПД | ✅✅ | Реализовано буквально (рантайм + кэш) |
| 9 Fallback | ⚠️ | Нет |
