# Контракт входа в Компас — `HandoffContext`

Что сервис «План развития» передаёт в Компас **в момент перехода** (когда сотрудник
жмёт «Создать через Компас»). Это входной контекст: с него начинается диалог.

Данные делятся на два типа:
- **A. Прямо в payload** — то, что нужно сразу и помещается в тело перехода.
- **B. По ссылке / API** — то, что тяжело или нужно не всегда; Компас дотягивает сам
  с переданным токеном.

Остальное (цель, приоритеты, целевая роль, самооценка) **появляется в диалоге** и во
входной контракт не входит.

---

## A. Передаётся прямо в payload

| Поле | Назначение |
|---|---|
| Токен доступа | аутентификация + право на запросы к API «Плана развития» |
| Инициатор (ID + роль: EMPLOYEE / HR / MANAGER) | кто создаёт; тон диалога, чей план |
| Сотрудник (ID, ФИО, подразделение, отдел) | на кого строим ИПР |
| Текущая должность: код, название, грейд | опорная точка |
| **ДИ текущей должности** (текст, **может быть пустой**) | основной документ для вопросов; пусто → fallback (новый сотрудник) |
| **Профиль текущей должности** (компетенции + **целевые уровни**) | что оцениваем и с чем сравниваем (расчёт разрыва) |
| Return-контекст (planId \| null, callbackUrl) | куда вернуть результат; null → создать новый ИПР |
| sessionId (\| null) | возобновление незаконченного диалога; null → новая сессия |

## B. Приходит по ссылке / API — Компас дотягивает сам

| Что | Когда | Как |
|---|---|---|
| Каталог должностей (**шире отдела** — подразделение/организация) | когда в диалоге названа целевая роль | поиск по API «Плана развития» по названию, с токеном |
| ДИ и профиль **целевой** должности | после выбора целевой роли в диалоге | lookup по коду найденной должности |

> Целевую должность узнаём только в диалоге, она за сотрудником заранее не закреплена.
> Поэтому каталог не кладём в payload (он большой) — Компас **ищет должность по названию**
> и **подтверждает выбор у человека** («вы имели в виду …?»), затем тянет её профиль.

## JSON-контракт

```jsonc
{
  "accessToken": "string",              // сессия + права на API «Плана развития»

  "initiator": {                        // кто создаёт
    "id": "string",
    "role": "EMPLOYEE | HR | MANAGER"
  },

  "employee": {                         // на кого строим ИПР
    "id": "string",
    "fullName": "string",
    "unit": "string",                   // подразделение
    "department": "string"              // отдел
  },

  "currentPosition": {                  // приходит телом — нужно сразу
    "code": "string",
    "title": "string",
    "grade": "string | null",
    "jobDescription": "string | null",  // ДИ; null → fallback (новый сотрудник)
    "profile": {
      "competencies": [
        { "code": "string", "name": "string", "targetLevel": "number" }
      ]
    }
  },

  "session": {
    "id": "string | null"               // null → новая сессия; иначе возобновляем
  },

  "return": {                           // куда вернуть результат
    "planId": "string | null",          // null → создать новый ИПР
    "callbackUrl": "string"
  }
}
```

Каталог должностей и профиль целевой роли (часть B) в payload не входят — запрашиваются
через API «Плана развития» с `accessToken` по ходу диалога.

---

## Что появляется в диалоге (не в контракте входа)
- Целевая должность / роль (поиск + подтверждение → затем профиль по API).
- Сценарий: новый / в должности / переход.
- Ключевая цель ИПР, приоритеты, горизонт, ограничения по времени.
- Самооценка по компетенциям.
- Что уже проходил.

## Следующий этап (пока вне контракта)
- Каталог развивающих активностей (Etutor / Locus) — ссылки на курсы/вебинары под разрыв.
- Предыдущий ИПР.
- Оценочный лист (сильные стороны, резервы развития) как объективный вход.

## Осознанные ограничения этапа 1
- План строится **на самооценке** (объективная оценка — следующий этап); самооценка
  субъективна — это принятый компромисс.
- Рекомендации по активностям **без привязки к живому каталогу** (нет интеграции с LMS) —
  общие, без проверки доступности и без учёта уже пройденного.

## Открытые вопросы к «Плану развития»
1. ДИ и профиль текущей должности реально отдаются **телом** в момент перехода, или только
   ID/ссылкой (тогда и они уходят в часть B)?
2. Поиск должностей (часть B) — какой **API и его границы** (подразделение / организация)?
3. Если инициатор — HR/руководитель, токен даёт доступ к ДИ/профилю **этого сотрудника**?
   (граница прав, иначе lookup вернёт 403)
