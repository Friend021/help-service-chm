# Контракт входа: «ПЛАН РАЗВИТИЯ» → «Компас»

Обе стороны интеграции в макете наши, поэтому контракт зафиксирован здесь.

## 1. Точка входа

Заглушка отдаёт страницу-форму на `http://localhost:8081/`. Кнопка
**«Сформировать с помощью Компаса»** ведёт на:

```
GET http://localhost:8081/kompas?employee=<externalId>
```

Заглушка формирует подписанный JWT и отвечает редиректом:

```
302 Location: http://localhost:4200/entry?token=<JWT>
```

Базовый URL «Компаса» задаётся переменной `KOMPAS_FRONTEND_URL`
(в контейнере — `LEGACY_KOMPAS_FRONTEND_URL`).

## 2. Токен входа

| Параметр | Значение |
|---|---|
| Алгоритм | HMAC-SHA256 (`HS256`) |
| Секрет | `JWT_SECRET` из `.env`, общий для заглушки и «Компаса», минимум 32 байта |
| TTL | 10 минут (`legacy.jwt-ttl`) |
| Передача | query-параметр `token` |

### Claims

| Claim | Обязателен | Описание |
|---|---|---|
| `employeeExternalId` | да | Идентификатор сотрудника во внешней системе |
| `fullName` | да | ФИО сотрудника |
| `currentPosition` | нет | Название текущей должности |
| `targetRole` | нет | Название целевой роли |
| `careerTrack` | нет | Карьерный трек |
| `managerFullName` | нет | ФИО руководителя |
| `managerExternalId` | нет | Идентификатор руководителя |
| `iss` | да | `legacy-plan-razvitiya` |
| `sub` | да | Дублирует `employeeExternalId` |
| `iat`, `exp` | да | Выдан / истекает |

Пример payload:

```json
{
  "iss": "legacy-plan-razvitiya",
  "sub": "emp-001",
  "employeeExternalId": "emp-001",
  "fullName": "Соколова Анна Дмитриевна",
  "currentPosition": "Разработчик Java",
  "targetRole": "Ведущий разработчик Java",
  "careerTrack": "Разработка ПО",
  "managerFullName": "Верещагин Олег Борисович",
  "managerExternalId": "mgr-001",
  "iat": 1790000000,
  "exp": 1790000600
}
```

## 3. Приём входа в «Компасе»

1. SPA открывает маршрут `/entry?token=...`, забирает токен из query.
2. SPA вызывает `POST /api/sessions` с телом `{"token": "<JWT>"}`.
3. Бэкенд проверяет подпись и срок (`JwtEntryTokenVerifier`).
4. По `employeeExternalId` находится или заводится `Employee`;
   `currentPosition` и `targetRole` сопоставляются со справочником должностей по названию
   (если должности нет — заводится запись без компетенций, контекст не теряется).
5. Создаётся `DialogSession` в стадии `CONTEXT`, ассистент делает первый ход.
6. В ответ приходит `accessToken` (TTL 12 часов) — им подписываются все последующие вызовы API
   заголовком `Authorization: Bearer <accessToken>`.

Разделение на два токена сделано намеренно: короткий TTL токена входа нужен
для безопасности перехода, но не должен обрывать диалог через 10 минут.

## 4. Поведение при ошибке

| Ситуация | HTTP | Что видит сотрудник |
|---|---|---|
| Нет параметра `token` | — | «В ссылке нет токена входа» |
| Подпись не сходится | 401 | «Токен входа недействителен или истёк» |
| Токен просрочен | 401 | То же + подсказка вернуться в «ПЛАН РАЗВИТИЯ» |
| Истёк `accessToken` | 401 | Редирект на `/entry` |

## 5. Пример кнопки в заглушке

```html
<a class="btn btn--kompas" th:href="@{/kompas(employee=${employee.externalId})}">
    Сформировать с помощью Компаса
</a>
```

## 6. Что меняется при переходе в бой — [POST-MVP]

- HMAC заменяется на асимметричную подпись или реальный SSO: нужна другая реализация
  `EntryTokenVerifier`, контракт claims сохраняется.
- Токен переносится из query в заголовок или в короткоживущий code-exchange.

# Обратный контракт: «Компас» → «ПЛАН РАЗВИТИЯ»

Готовый план возвращается в форму старого сервиса. Схема зеркалит вход:
тот же общий секрет, короткий TTL, передача подписанным токеном в ссылке.
Серверного вызова между сервисами нет — сотрудник сам уходит по ссылке.

## 1. Получение ссылки

```
POST /api/idp/{id}/handover
Authorization: Bearer <accessToken>

200 {"url": "http://localhost:8081/import?token=<JWT>"}
409 — в плане нет приоритетов, переносить нечего
```

Адрес формы задаётся переменной `LEGACY_IMPORT_URL`
(в контейнере — `KOMPAS_LEGACY_IMPORT_URL`).

## 2. Токен переноса

| Параметр | Значение |
|---|---|
| Алгоритм | HMAC-SHA256, тот же `JWT_SECRET` |
| TTL | 10 минут (`kompas.legacy.handover-ttl`) |
| Размер | около 2,5 КБ на план из трёх приоритетов |

### Claims

| Claim | Описание |
|---|---|
| `employeeExternalId` | По нему форма выбирает сотрудника в шапке |
| `employeeName`, `managerName` | Блок реквизитов карточки |
| `currentPosition`, `targetRole` | Текущая должность и ориентир |
| `date` | Дата составления плана (ГГГГ-ММ-ДД) |
| `priorities` | Строки таблицы, см. ниже |
| `iss` | `kompas` |
| `sub` | Идентификатор ИПР |

### Раскладка по колонкам формы

Каждый элемент `priorities` — одна строка блока «Приоритеты развития»,
**отсортированная по номеру приоритета**:

| Поле токена | Колонка формы |
|---|---|
| `order` | «Приоритет» |
| `category` | «Цели по развитию» — **значение выпадающего списка** |
| `competencies` | «Что развиваем?», первая строка — названия через `; ` |
| `goal` | «Что развиваем?», вторая строка — формулировка SMART |
| `activities` | «Что развиваем?», третья строка |

Компетенции и активности передаются **названиями, а не кодами**: коды —
внутренний идентификатор «Компаса», старому сервису они не нужны.

### Справочник «Цели по развитию»

Эта колонка формы — **не свободный текст, а выпадающий список** с фиксированным
набором значений. Он принадлежит старому сервису:

```
Цели развития не определены/Развитие не требуется   Развитие управленческих компетенций
Адаптация к должности                               Кадровый резерв на должность/роль
Повышение объемов производства                      Адаптация к процессам
Увеличение скорости выполнения задач                Изучение продуктов
Увеличение качества выполняемых задач               Изучение инструментария и технологий
Развитие личностных компетенций
```

«Компас» относит каждый приоритет к одной из этих рубрик: список подаётся
ассистенту в RAG-контексте, а `DraftParser` сверяет ответ со справочником
и отбрасывает всё, чего в нём нет — произвольная формулировка в выпадающий
список формы не встанет.

**Список продублирован в двух местах** и должен совпадать:
`backend/.../seed/reference-data.yml` (`goalCategories`) и
`legacy-stub/.../application.yml` (`legacy.goal-categories`). В боевой интеграции
«Компас» будет получать его из старого сервиса, а не хранить копию.

## 3. Приём в форме

`GET /import?token=<JWT>` проверяет подпись и срок (`HandoverTokenVerifier`)
и рендерит ту же страницу с заполненной таблицей и пометкой
«Приоритеты перенесены из „Компаса“». Недействительный или просроченный токен —
та же форма с красным сообщением и пустой таблицей, без падения.

## 4. Ограничение макета

План переносится **в отображение формы**, а не в базу старого сервиса:
своего хранилища у заглушки нет. В боевой интеграции этот шаг заменяется
записью приоритетов в БД сервиса «ПЛАН РАЗВИТИЯ» — состав полей уже совпадает.
