# Постановка задачи: сервис «Компас» (боевая реализация)

Задача для команды разработки. Нужно построить внутренний сервис формирования ИПР.
**Кода нет — пишем с нуля.** Есть работающий **прототип (MVP)**, который демонстрирует
целевое поведение целиком; он служит эталоном, а не основой — боевую версию делаем
заново, во внутреннем контуре компании.

---

## 1. Что за сервис и зачем

Формирование индивидуального плана развития (ИПР) в рамках ежегодной оценки — ручной
процесс «с чистого листа». Существующий сервис **«ПЛАН РАЗВИТИЯ»** даёт пустую форму,
но не помогает осмысленно собрать план.

«Компас» встраивается перед этой формой: в диалоге оценивает разрыв между текущей
и целевой ролью, выявляет интересы и за несколько итераций собирает черновик ИПР
с целями, развивающими действиями и сроками. Рекомендации **заземлены на справочники
компании** (должностные инструкции, модель компетенций, каталог активностей) — план
из реального контекста, а не абстрактный. Готовый план возвращается в форму
«ПЛАН РАЗВИТИЯ».

---

## 2. Прототип как эталон

Прежде чем проектировать — пройти сквозной сценарий в прототипе, чтобы увидеть
целевое поведение: вход из формы → диалог по стадиям → живой черновик → экспорт
и возврат в форму.

**Что прототип упрощал — и что в бою делаем по-настоящему:**

| Прототип (MVP) | Боевая версия |
|---|---|
| Внешняя LLM (OpenRouter) | Внутренний шлюз **`ai.redelephant`**, без внешних вызовов |
| Локальные эмбеддинги (хеширование) | Настоящая модель эмбеддингов |
| Косинус в памяти | Векторное хранилище (pgvector или аналог) |
| HMAC-токен входа | Реальный **SSO** |
| Справочники в сиде, продублированы | Из систем-источников компании, единый источник |
| Перенос = отрисовка формы | **Запись** приоритетов и действий в БД/через API «ПЛАНА РАЗВИТИЯ» |
| Данные синтетические | Реальные, обрабатываются только во внутреннем контуре |
| Заглушка «ПЛАН РАЗВИТИЯ» | Интеграция с реальным сервисом |

Схема потока — [`kompas-schema.drawio`](kompas-schema.drawio).
Контракты входа и возврата — [`integration.md`](integration.md).

---

## 3. Архитектура и разделение команд

```
Frontend (SPA) ──REST──> Backend ──> внутренняя LLM (ai.redelephant)
                              └─────> PostgreSQL + векторное хранилище
                              └─────> справочники компании
                              └─────> сервис «ПЛАН РАЗВИТИЯ» (вход и возврат)
```

**Шов между командами — REST API.** Контракт фиксируется первым; дальше backend
и frontend работают параллельно. Фронт разрабатывает против мока/стабов, не дожидаясь
готовности LLM-части. Все вызовы, кроме создания сессии и health, под токеном доступа.

---

## 4. Backend — что реализовать

**Диалоговый движок**
- Стадии: `CONTEXT → GAP_ANALYSIS → INTERESTS → DRAFT → REFINE → FINALIZE`.
- Оркестратор: собирает промпт (система + стадия + состояние сессии + контекст + история),
  вызывает LLM, разбирает ответ, обновляет состояние и черновик.
- **Переходы между стадиями — детерминированы в коде**, не отданы модели (иначе диалог
  зависает). Защита от зацикливания стадии.
- Промпты — версионируемые файлы вне кода, на русском.

**Заземление (критично)**
- Ответ модели — строго машиночитаемый JSON + текст для чата. Парсер с валидацией
  и повторным запросом при неверном формате.
- **Санитайз: из плана вычищается всё, чего нет в справочниках** (компетенции,
  активности, рубрики, инструменты). Ассистент не должен выдумывать — ни кода, ни курса.

**LLM и RAG**
- LLM за интерфейсом → реализация `ai.redelephant`. Подмена конфигом. Никаких внешних
  вызовов в бою.
- Эмбеддинги за интерфейсом — внутренняя/локальная модель.
- Ретривер по справочникам: ДИ целевой роли, модель компетенций (все компетенции роли),
  каталог активностей (связанные + поиск по запросу). Векторное хранилище.

**Доменная модель и хранилище (PostgreSQL)**
- Сотрудник, роли/должности, компетенции, активности.
- Сессия диалога, сообщения.
- ИПР → приоритеты → развивающие действия (инструмент, конкретное действие, срок,
  статус), статусы согласования.

**Выходы**
- Экспорт DOCX / JSON.
- Согласование: статус `ON_APPROVAL` + уведомление руководителю (реальный канал).
- **Возврат в «ПЛАН РАЗВИТИЯ»**: разложить план по колонкам формы (рубрика цели —
  из её справочника, инструмент действия — из её справочника) и записать в её БД/через API.

**Безопасность**
- Приём входа (SSO), выдача токена доступа, разграничение доступа по сотруднику.

**Справочники**
- Рубрики целей, инструменты развития, каталог активностей, модель компетенций —
  из систем-источников. Единый источник, без дублей.

## 5. Frontend — что реализовать

**Экран входа**
- Приём токена, инициализация сессии, обработка невалидного/просроченного входа.

**Чат**
- Диалог с ассистентом, индикатор стадии (шаг N из 6), ввод.
- **Стриминг ответа** — рендер по мере генерации (ответ модели не мгновенный).

**Панель ИПР (живой черновик)**
- Таблица приоритетов, как в форме «ПЛАН РАЗВИТИЯ»: приоритет / цель по развитию
  (рубрика) / что развиваем.
- Под каждой целью — блок развивающих действий: инструмент (выпадающий список),
  конкретное действие, срок, статус.
- **Ручная правка**: менять, добавлять, удалять приоритеты и действия.

**Действия с планом**
- Экспорт (скачивание DOCX/JSON), отправка на согласование, перенос в «ПЛАН РАЗВИТИЯ».

**Общее**
- Корпоративный UI-kit. Шрифты и иконки — локально (внутренний контур, без внешних CDN).
- Интерсептор токена, понятные состояния загрузки и ошибок. Весь интерфейс на русском.

## 6. Нефункциональные требования

- **Приватность.** ИПР и результаты оценки — чувствительные данные. Обработка **только
  во внутреннем контуре**, никакой внешней LLM. Это причина `ai.redelephant`.
- **Конфигурируемость.** Провайдер LLM, verifier токена, notifier согласования,
  формат экспорта — через конфиг. Секреты — вне репозитория.
- **Воспроизводимость деплоя.**
- Логи без PII и содержимого ИПР выше DEBUG.

## 7. Критерии приёмки

1. Сотрудник из формы «ПЛАН РАЗВИТИЯ» переходит в «Компас» с корректным контекстом.
2. Диалог проводит по стадиям и собирает черновик минимум на одном карьерном треке.
3. Черновик опирается на **реальные** компетенции роли и активности каталога — не
   выдуманные; коды вне справочников отбрасываются.
4. План правится вручную в панели.
5. Готовый план экспортируется (DOCX + JSON) и отправляется на согласование.
6. План **записывается обратно** в «ПЛАН РАЗВИТИЯ»: рубрики и инструменты из её
   справочников, приоритеты и действия по колонкам формы.
7. Весь контур — внутренний, на `ai.redelephant`, без внешних вызовов.

## 9. Эпики и задачи (для трекера)

Разбивка для импорта в трекер. Владелец: **BE** — backend, **FE** — frontend,
**BE+FE** — на стыке, согласуют контракт. Оценка грубая: **S** ≤ 2 дней,
**M** до недели, **L** 1–2 недели. У каждой задачи — критерий готовности (DoD).

### E1. Каркас и запуск · BE+FE
- **[BE+FE · M]** Репозиторий, сборка, профили, деплой во внутренний контур.
  *DoD: пустые модули собираются и стартуют одной командой.*
- **[BE · S]** Конфигурация через env + профили; секреты вне репозитория.
  *DoD: провайдер LLM, verifier, notifier переключаются конфигом.*
- **[BE+FE · M]** CI: сборка, тесты, линт на каждый PR. *DoD: пайплайн зелёный.*

### E2. Вход и сессия (SSO) · BE+FE
- **[BE · M]** Приём входа: проверка токена/SSO, создание или поиск сотрудника,
  сопоставление должности и целевой роли, создание сессии.
  *DoD: валидный вход открывает сессию, невалидный — понятная ошибка.*
- **[BE · S]** Токен доступа (обмен на входе), разграничение по сотруднику.
  *DoD: чужую сессию/ИПР получить нельзя.*
- **[FE · S]** Экран входа: принять токен, стартовать сессию, обработать ошибку.
  *DoD: при невалидном токене — сообщение и путь назад.*

### E3. Диалоговый движок · BE
- **[BE · L]** Оркестратор стадий `CONTEXT→GAP→INTERESTS→DRAFT→REFINE→FINALIZE`:
  сборка промпта, вызов LLM, разбор ответа, обновление состояния.
  *DoD: сквозной диалог собирает черновик минимум на одном треке.*
- **[BE · M]** Переходы между стадиями детерминированы в коде; защита от зацикливания.
  *DoD: диалог не зависает на стадии, не переспрашивает отвеченное.*
- **[BE · S]** Промпты — версионируемые файлы вне кода. *DoD: правка промпта без пересборки логики.*
- **[BE · M]** Парсер ответа: строгий JSON, повтор при неверном формате, fallback.
  *DoD: кривой ответ модели не роняет ход.*

### E4. Заземление и RAG · BE
- **[BE · L]** Ретривер: ДИ целевой роли, все компетенции роли, каталог активностей
  (связанные + поиск по запросу). *DoD: контекст собирается из справочников.*
- **[BE · M]** Векторное хранилище (pgvector) + индексация справочников.
  *DoD: поиск по каталогу возвращает релевантные активности.*
- **[BE · M]** Санитайз черновика: отбрасывать коды/рубрики/инструменты вне справочников.
  *DoD: план не содержит ничего, чего нет в справочниках.*

### E5. LLM-интеграция (ai.redelephant) · BE
- **[BE · M]** Реализация `ai.redelephant` за интерфейсом LLM-клиента.
  *DoD: диалог работает на внутреннем шлюзе, без внешних вызовов.*
- **[BE · M]** Эмбеддинги за интерфейсом — внутренняя/локальная модель. *DoD: индекс строится на ней.*
- **[BE · S]** Стриминг ответа (SSE) для фронта. *DoD: ответ отдаётся по мере генерации.*

### E6. Доменная модель и хранилище · BE
- **[BE · M]** Сущности и миграции: сотрудник, роли, компетенции, активности,
  сессия, сообщения, ИПР, приоритеты, развивающие действия, статусы.
  *DoD: схема под весь сценарий, миграции воспроизводимы.*
- **[BE · S]** Сервис ИПР: применение черновика, статусы, ручная правка. *DoD: план корректно обновляется.*

### E7. Чат · FE
- **[FE · M]** Диалог с ассистентом, индикатор стадии, ввод. *DoD: виден прогресс по стадиям.*
- **[FE · M]** Стриминг ответа в UI. *DoD: текст появляется по мере генерации.*

### E8. Панель ИПР · FE
- **[FE · L]** Живая таблица приоритетов (приоритет / цель-рубрика / что развиваем)
  + блок развивающих действий под каждой целью. *DoD: панель повторяет структуру формы.*
- **[FE · M]** Ручная правка: инструмент (список), действие, срок; добавление/удаление.
  *DoD: правка сохраняется и соответствует контракту.*

### E9. Экспорт · BE+FE
- **[BE · M]** Генерация DOCX и JSON. *DoD: DOCX открывается, структура — как в форме.*
- **[FE · S]** Кнопка экспорта и скачивание. *DoD: файл скачивается.*

### E10. Согласование · BE+FE
- **[BE · M]** `submit` → статус `ON_APPROVAL` + уведомление руководителю (реальный канал).
  *DoD: руководитель получает уведомление, статус меняется.*
- **[FE · S]** Кнопка отправки, блокировка правки после отправки. *DoD: отправленный план не редактируется.*

### E11. Возврат в «ПЛАН РАЗВИТИЯ» · BE+FE
- **[BE · L]** Запись приоритетов и действий в БД/через API старого сервиса:
  рубрики и инструменты из его справочников, раскладка по колонкам формы.
  *DoD: план появляется в форме как штатно созданный.*
- **[FE · S]** Кнопка переноса и переход. *DoD: сотрудник попадает в заполненную форму.*

### E12. Справочники · BE
- **[BE · M]** Загрузка модели компетенций, каталога активностей, рубрик целей
  и инструментов из систем-источников; единый источник. *DoD: без дублей, обновляемо.*

### E13. Приватность и наблюдаемость · BE+FE
- **[BE · S]** Контур только внутренний, внешних вызовов нет. *DoD: проверено на сетевом уровне.*
- **[BE · S]** Логи без PII и содержимого ИПР выше DEBUG. *DoD: в логах нет чувствительных данных.*
- **[BE+FE · M]** e2e-тест сквозного сценария (вход → диалог → правка → перенос).
  *DoD: тест проходит в CI.*
